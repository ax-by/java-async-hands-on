### 모범 답안 (solutions/ 폴더에만 있음)

## 결정
- 목적: **A (병렬 blocking fan-out)**
- 한 줄 근거: 독립적인 blocking SDK 호출 4개(120/150/100/80ms)를 전용 풀에서 동시에 실행해 합 450ms → 최댓값 150ms 로 줄인다. SDK 가 blocking 이라 B 는 불가능하다.

## 근거
- 독립적인 호출: 네 공급사 모두 route 만 입력으로 받고, 서로의 결과를 쓰지 않는다.
- 클라이언트 특성: SDK 가 결과를 반환값으로 주고(future/콜백 없음) 문서상 "호출 스레드를 막는다". → blocking (Q2: 아니오 → A).
- 기대 효과: 순차 450ms → 병렬 ≈150ms (p50). 실패 시에도 ≤ 300ms. 요청당 점유 스레드는 줄지 않는다(4개, 요청 스레드 대신 vendor 풀 스레드가 막힐 뿐) — A 를 B 라고 부르지 않는다.

## 실행 모델
- `supplyAsync`/submit 한 SDK 호출: [vendor] / [blocking] (R3: 제출만 하고 즉시 반환 → search() 는 막히지 않는다).
- `allOf(..).thenApply(조립)`: 마지막에 완료된 분기를 완료시킨 스레드(R1 표). 보통 vendor 스레드, 공급사가 시간 초과면 **JDK 타임아웃 스케줄러**. 조립은 리스트 정렬뿐이라(< 1ms) 어느 스레드여도 괜찮다. 여기서 blocking 하면 JVM 전체의 타임아웃이 밀리므로(R10) 절대 blocking 을 넣지 않는다.
- executor: `vendor` 전용 ThreadPoolExecutor, **128 스레드**, 큐 256(ArrayBlockingQueue), **AbortPolicy**.
  - 크기 근거: 초당 200 검색 × 0.15s = 동시 30 검색, × 4 호출 = 동시 120 blocking 호출 → 128.
  - **큐를 너무 작게 두면 안 되는 이유**: `ThreadPoolExecutor`는 스레드 수가 코어(128)에 도달하면 **놀고 있는 스레드가 있어도 작업을 큐를 거쳐 전달한다.** 동시 검색 30건이 한꺼번에 들어와 120개를 연속 제출하면, 놀던 워커들이 큐에서 꺼내 가기 전에 큐 64가 순간적으로 넘쳐 **멀쩡한 공급사가 거절**된다(실측: 웨이브마다 0~9건). 큐는 "제출 순간의 버스트"를 흡수할 만큼(≥ 동시 호출 수) 둔다.
  - 대기 시간의 상한은 큐 크기가 아니라 **공급사별 타임아웃 250ms**가 정한다. 타이머는 제출 시점에 시작하므로, 큐에서 250ms를 넘게 기다리면 그 공급사는 unavailable이 되고 `cancel(true)`로 큐의 작업도 실행되지 않는다.
  - 대안: `SynchronousQueue`(큐 없이 직접 전달, 128개가 모두 바쁠 때만 거절)도 같은 테스트를 통과한다. 다만 워커가 작업 사이에 잠깐 빈 순간에도 거절될 수 있다는 점을 알고 쓴다.
  - CallerRuns 금지: 거절된 SDK 호출이 요청 스레드에서 실행되면 search() 가 막힌다(R3 예외 1).
  - 다운스트림 확인: 공급사별 동시 연결 한도(SDK 커넥션 풀)가 30 이상인지 확인해야 한다.
- blocking 지점: 네 SDK 호출 → 모두 vendor 스레드. 요청 스레드·commonPool 에는 blocking 없음.

## 실패 모델
- 공급사별 타임아웃 250ms (`orTimeout` 을 **결과 future 자체**에 건다). 각 분기는 `handle` 로 실패를 null 로 바꿔 절대 실패하지 않는다 → allOf 는 늦어도 ≈250ms 에 완료 → SLO 300ms.
- 부분 실패: 실패/초과 공급사는 `unavailable` 에 이름, 검색은 성공. 예외 판별을 하지 않으므로 unwrap 이 필요 없다(실패면 무엇이든 unavailable).
- 타임아웃 후 남은 작업 (R10): `orTimeout` 은 future 만 실패시키고 SDK 호출은 계속 스레드를 잡는다. 그래서 `executor.submit()` 이 준 `Future` 를 보관하고, 시간 초과되면 `Future.cancel(true)` 로 **interrupt** 한다(SDK 가 interrupt 를 지원한다). 큐에 있던 작업은 실행되지 않는다.
- 과부하 정책: 설계 한도(동시 30)를 넘어 풀·큐가 차면 그 공급사는 unavailable 로 즉시 처리(부분 결과). 더 근본적으로는 앞단(게이트웨이)의 동시 요청 제한(bulkhead)과 503 을 둔다.

## 틀렸다면 보일 증상
- executor 생략(commonPool): parallel stream 등 무관한 작업 지연, Java 17 소형 컨테이너에서는 요청마다 스레드 생성(버전표).
- interrupt 없이 orTimeout 만: 응답은 300ms 인데 vendor 풀 active 가 계속 증가 → 결국 큐 적체·거절 → 모든 공급사 unavailable.
- 풀이 작으면(예: 16): 피크에 큐 대기 → 공급사별 250ms 초과 → 정상인데도 unavailable 증가, p99 상승.
- 전체 타임아웃만 있고 공급사별 타임아웃이 없으면: 한 공급사 장애로 전체 검색이 실패한다(부분 결과 불가).
- 조립 단계에 blocking(로그 원격 전송 등)을 넣으면: 타임아웃 스케줄러가 막혀 다른 모든 타임아웃이 늦게 발화.
