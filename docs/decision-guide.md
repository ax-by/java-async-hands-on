# 판단 가이드: CF를 쓸 것인가, 쓴다면 A인가 B인가

설계 실습(m05, m06, m08, m11)은 코드를 쓰기 전에 각 실습 폴더의 `DECISION.md`를 먼저 채운다. 이 문서는 그 판단 순서다.

## 1단계: 질문 흐름

```
Q1. 이 작업에 I/O 호출이 2개 이상 있고, 그중 서로 독립적인(앞 결과가 필요 없는) 호출이 있는가?
    ├─ 아니오 → Q4
    └─ 예 → Q2
Q2. 지금 쓰는 드라이버/클라이언트가 진짜 비동기인가? (future/콜백을 반환하고 I/O 동안 스레드를 잡지 않는가)
    ├─ 아니오 (JDBC, RestTemplate, 파일 I/O) → A 후보 → Q3
    └─ 예 (Lettuce, WebClient, JDK HttpClient.sendAsync, AWS SDK v2 async) → B 후보 → Q5
Q3. [A] 병렬화로 줄어드는 시간이 의미 있는가? (예: 300ms → 100ms, 응답 SLO에 영향)
    ├─ 예 → A: 전용 blocking 풀 + 전체 타임아웃 + 실패 정책
    └─ 아니오 → 쓰지 않음 (동기 코드)
Q4. 호출 쪽이 이미 비동기 API를 요구하는가? (프레임워크가 CompletionStage를 받는다, 라이브러리 공개 API다)
    ├─ 예 → B 파이프라인의 일부로 설계 (Q5)
    └─ 아니오 → 쓰지 않음
Q5. [B] 파이프라인 전체에서 blocking 호출을 0으로 만들 수 있는가?
    ├─ 예 → B
    └─ 아니오 (중간에 JDBC가 꼭 필요) → B + "격리 구간": 그 호출만 전용 blocking 풀로 보낸다 (`supplyAsync(.., blockingPool)` + `thenCompose`).
        이때 전체가 B라고 말하면 안 된다. "B, 단 X 구간은 A식 격리"라고 설명한다.
```

## 2단계: DECISION.md 양식

```markdown
## 결정
- 목적: A / B / 쓰지 않음
- 한 줄 근거:

## 근거
- 독립적인 호출: (어떤 호출들이, 왜 독립적인가)
- 클라이언트 특성: (blocking / non-blocking, 무엇을 보고 판단했나)
- 기대 효과 (숫자로): 예) 순차 300ms → 병렬 100ms, 또는 요청당 점유 스레드 1 → 0

## 실행 모델
- 각 단계의 실행 스레드: (R1/R2 근거와 함께)
- executor: 이름, 크기, 큐, 거절 정책, 그리고 그 크기의 근거 (R11)
- blocking 지점과 그 지점이 실행되는 스레드:

## 실패 모델
- 전체 타임아웃:            부분 실패 정책: (전체 실패 / 폴백 / 부분 결과)
- 예외 unwrap 위치:          타임아웃 후 남은 작업 처리: (R10)

## 이 설계가 틀렸다면 어떤 증상이 보일까
- 예) 이벤트 루프 lag 증가, 풀 큐 적체, p99만 튐 ...
```

## 3단계: 근거의 품질 기준 (자기 점검)

| 등급 | 근거 예시 |
|---|---|
| 불합격 | "비동기라서 빠르다", "논블로킹이 좋으니까" |
| 부족 | "두 호출을 병렬로 실행하려고" (얼마나 줄어드는지, 어떤 풀에서인지가 없다) |
| 합격 | "user(100ms)와 price(120ms)는 서로 독립이고 둘 다 JDBC(blocking)라 A. 전용 풀 `io`(8, 큐 100, AbortPolicy → 503)에서 병렬로 실행해 220ms → 120ms. 전체 타임아웃 300ms, price 실패 시 기본 가격으로 폴백" |
